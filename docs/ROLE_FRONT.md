# 프론트 (앱 전부) 할 일 — 윤재열

> 문서의 "프론트 (앱)" 탭을 옮긴 것이다 (11/11 기준). 규칙과 API·데이터 클래스는 루트 `CLAUDE.md`의 공통 규약을 따른다.

프론트(윤재열)는 안드로이드 앱 전부를 혼자 맡는다. 개발 20~27시간 + 통합·발표 파트 4~5시간. 서버가 없어도 가짜 서버 응답(Fake)으로 끝까지 만들고, 백이 서버를 push하면 내 노트북에서 서버를 켜서 붙인다. 막히면 카톡 → 그래도 안 풀리면 그때 만난다.

## 맡는 범위

- `DalmuriBus/` 전부: gradle·Manifest·데이터 클래스, 로그인, 화면, ViewModel, Retrofit, Room, Fake 서버
- 지도 화면: 서버에서 받아 둔 지도 이미지 + 위에 정류장·버스·노선 그리기 (교수님: "클라이언트는 명확한 것 + 화면·지도 팔로업")
- 서버와 연결 확인 (자기 노트북에서 서버를 직접 켜서)
- 추가 기능 화면: 이용 내역, 하차 요약, 호출 취소
- 발표·보고서·시연 영상의 앱 파트

## 할 일

### 1주차 (11/12~11/20)

- [ ] **F0. 프로젝트 기본 세팅 (1~2h)** — 레포 main에는 아직 제안서/만 있으니 안드로이드 프로젝트를 `DalmuriBus/` 폴더째 처음 push하고 백에게 카톡
  - gradle: Retrofit + Gson 변환기, OkHttp(로깅), Room + KSP, Navigation-Compose, lifecycle-viewmodel-compose, Firebase Auth (BoM은 이미 있음)
  - Manifest: 인터넷 권한, 평문(http) 통신 허용, `android:name=".DalmuriApp"`
  - `data/model/`: 공통 규약 4의 클래스 그대로
  - 완료 기준: 빌드 성공
- [ ] **F1. 로그인 먼저 끝내기 (2~3h)** — 교수님: "범위가 명확한 건 미리 후딱 해치워라"
  - Firebase 콘솔에서 이메일/비밀번호 로그인은 이미 켜져 있음
  - 로그인·회원가입 화면 하나 (이메일, 비밀번호, [로그인], [회원가입]), 로그인돼 있으면 바로 메인으로
  - 완료 기준: 가입 후 Firebase 콘솔 Authentication 사용자 목록에 생기고, 앱을 다시 켜면 바로 메인
- [ ] **F2. 앱 뼈대 (2h)**
  - 다크 테마 (승차 = 블루, 하차 = 달빛 골드 포인트 컬러)
  - Navigation: `"login"` → `"map"` (메인). 추가 기능용 `"history"`는 자리만
  - 메인 화면 = 지도 영역(지금은 회색 박스) + 하단 시트 구조
  - `DalmuriApp`(Application)에 간단한 컨테이너: API, 저장소를 여기서 꺼내 씀
- [ ] **F3. 서버 연결부 (2~3h)**
  - `DalmuriApi`: Retrofit 인터페이스 (`GET /stops`, `GET /map`, `GET /map/image`(파일 다운로드), `POST /calls`, `GET /calls/{callId}`)
  - `FakeDalmuriApi`: 같은 인터페이스를 메모리로 구현. 정류장 몇 개, 지도 정보(이미지는 임시 그림이나 회색), 호출하면 시간이 지나며 `REQUESTED → ASSIGNED → ONBOARD → COMPLETED`, 버스 좌표가 조금씩 이동, 합승 확인용으로 가끔 `route`에 다른 `callId` 섞기
  - `AppConfig.USE_FAKE_SERVER`, `AppConfig.BASE_URL = "http://10.0.2.2:3000/"`
  - 완료 기준: Fake로 호출하면 상태가 순서대로 바뀌는 게 Logcat에 찍힘
- [ ] **F4. 처음 실행 때 데이터 받아 저장 (2~3h)** — 교수님: "서버와 같은 구조로 Room에, 처음 뜰 때 받고 있으면 안 받음"
  - Room: `StopEntity`(`stops`), `MapInfoEntity`(`map_info`), DAO, `AppDatabase`
  - `MapRepository`: Room에 지도 정보가 없으면 `GET /map` + 이미지를 받아 `map_<mapId>.png`로 저장, 있으면 저장된 것만 사용. `StopRepository`도 같은 방식
  - 완료 기준: 두 번째 실행부터는 서버(또는 Fake)를 꺼도 정류장과 지도 이미지가 나옴

### 2주차 (11/18~11/27)

- [ ] **F5. 지도 화면 (4~5h)** — 교수님: "지도 레이아웃 하나 + 그 위에 겹쳐서 점을 찍는다"
  - `ui/map/MapLayer.kt`: `Box` 안에 아래 `Image`(저장된 지도) + 위 `Canvas`(정류장 점, 선택된 출발·도착 강조, 버스 🚌, 노선선)
  - 위도·경도 → 픽셀 변환은 공통 규약 5의 식. 단위 테스트 하나 붙이기 (모서리 좌표가 이미지 모서리로 가는지)
  - 노선선: `path`가 비어 있으면 버스 위치 → `route` 정류장들을 직선으로, 있으면 `path` 그대로
  - 핀치 줌·드래그 이동, 점을 누르면 정류장 선택 (탭 위치 → 가장 가까운 정류장), 구석에 `attribution` 글자
  - 완료 기준: Fake 데이터로 지도 위에 정류장·버스·노선이 맞는 자리에 보이고, 줌해도 같이 따라감
- [ ] **F6. 호출 화면 (3h)**
  - 지도에서 정류장을 눌러 출발 → 도착 순서로 선택 (하단 시트 목록으로도), 같은 정류장 막기, 다시 고르기
  - 탑승 인원 1~3명 선택 → [호출] → `POST /calls` → 받은 `callId`(배차 ID) 저장
- [ ] **F7. 상태 하단 시트 + 주기 조회 (3~4h)** — 교수님: "배차 ID로 예를 들면 10초에 한 번씩 요청해서 지도에 출력" (팀 결정으로 2초)
  - `TripViewModel`: `callId`가 생기면 `POLL_MS`마다 `GET /calls/{callId}` (코루틴 루프, `COMPLETED`·`REJECTED`면 멈춤, 화면 꺼지면 멈춤) → `StateFlow<CallDetail?>`
  - 시트 5종: 배차 중 / 버스 오는 중(몇 호차, N분 후 탑승) / 탑승 중(N분 후 하차, 남은 경유 정류장) / 하차 완료 / 배차 불가(다시 호출)
  - 받은 `bus`, `route`, `path`로 지도를 다시 그림 (노선이 바뀌면 받은 대로). 버스는 이전 위치 → 새 위치로 POLL_MS(2초) 동안 부드럽게 옮김 (Animatable 등)
  - 완료 기준: Fake로 호출부터 하차 완료까지 시트와 지도가 끊김 없이 바뀜
- [ ] **F8. 실제 서버에 붙이기 (1~2h, 백이 push한 뒤 · 11/21 무렵)**
  - pull → `server/README.md`대로 내 노트북에서 서버 실행 (Node.js 필요) → `USE_FAKE_SERVER = false`
  - 첫 실행 데이터 받기 → 호출 → 배정까지 확인. 막히면 `10.0.2.2`, 평문 통신 허용, 방화벽 순서로 확인하고, 서버 문제 같으면 백에게 카톡
